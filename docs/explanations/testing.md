# Testing

Caliper's tests use doctest and run through ctest. This page describes the layers that exist, what each proves, and how the tests that need a GPU report when there is none. The sources are in `tests/`, and `tests/CMakeLists.txt` registers them.

## The fast unit suite

`caliper_tests` is one executable that needs no window and no GPU. It holds the layers below, one source file per layer.

| Layer | What it proves |
|---|---|
| Manifest | The parser accepts a valid manifest, rejects a missing or malformed field, validates the applet id and ignores unknown keys. |
| Negotiation | The pre-load checks run in order: epoch, `min_host`, then required services, each with its refusal message. |
| Loader | The loader scans a folder, launches the `hello` applet through its full lifecycle, tears down an old instance before a relaunch, checks that the descriptor agrees with the manifest, shows a missing binary as a failed card, and refuses a path-escaping id. |
| Crash guard | A fault or an exception in an applet call is contained and reported, in the frame call and in a background job. The exception cases use `tests/fixtures/throwing_applet`, a hand-written descriptor that throws across the ABI, which the sugar would otherwise catch. |
| UI recovery | The host's UI stack is unwound after an applet fault left windows, plots and style pushes open. |
| Frame watchdog | Three consecutive slow frames latch the flag, a good frame resets the streak, and the flag stays until it is reset. |
| Services | Each service store and wrapper has its own tests: jobs, device, metrics, feed, artifacts, data and the tensor bridge. |
| Sugar | `CALIPER_APPLET`, the typed service wrappers, exception catching at the ABI edge and a run at a `dpi_scale` of 2. |
| ABI | `test_abi.cpp` asserts that the ABI structs are standard layout with `struct_size` first, and checks the epoch and every published table. |
| C compile check | `abi_c_check.c` includes every public header, newest first, in a C translation unit, so a header that is missing its own includes cannot hide behind another one. |

The same executable also covers the applet-side logic that needs neither torch nor a window, such as the instanced pose helper, the pulse ring and the export affordance.

The `hello` applet and `throwing_applet` are built first, because the loader tests load them from the build folder.

## The fixture host

`sdk/testing/caliper/fixture_host.h` is a headless fake `CaliperHost`. It serves `caliper.log.v1` and returns `NULL` for every other service, and a test can inject a table for any other service with `provide`. It lets an applet's logic and the sugar run without launching the UI. Only one fixture exists per process. The CMake target is `caliper::sdk_testing`; see [C++ sugar](../references/sugar.md) for its use in an applet's own tests.

## The pixel-exact graphics suite

`caliper_gfx_tests` (`tests/gfx/gfx_main.cpp`) checks the path from a tensor to a texture and the geometry path. It opens a hidden window, so it needs a graphical session. Every case reads the texture back from the GPU and compares it byte for byte with a CPU reference, which is the same reference the staged upload path uses.

The suite runs once per backend that the platform offers:

- OpenGL runs everywhere, as the fallback.
- Metal runs on macOS when a Metal device is present. It also covers the device paths, built from raw `MTLBuffer` allocations: the compute path for `f32` with a lookup table, the blit path for `u8`, stream-ordered updates, imported allocations and their gates, and the geometry service.
- Vulkan runs on Windows with the CPU-staged path. Cases that need CUDA hardware run only when a CUDA device is present.

`caliper_export_tests` does the same for `caliper.export.v1`: it drives the service as an embedder would and decodes the PNG it wrote. Its sidecar, atomic-write and sugar cases need no GPU.

Both suites open their windows hidden and never show or focus them, and on macOS the test process shows no Dock icon and no menu bar while it runs. GLFW's own initialisation would give it both: unless the init hint `GLFW_COCOA_MENUBAR` is false, it builds a menu bar and sets the activation policy to `NSApplicationActivationPolicyRegular`. The suites start GLFW through `tests/glfw_background.h` instead, which sets that hint to false and sets the policy to `NSApplicationActivationPolicyProhibited` before and after `glfwInit()` (`src/host/background_process.h`). One case in each suite checks that the policy still holds once the window exists.

The app itself takes the same mechanism with `--hidden` or `CALIPER_HIDDEN=1` ([The hidden window](../references/cli.md#the-hidden-window)): the real app, with its renderer and its frame loop, and a window that is never shown or focused. The ctest entry `caliper_cli_app_hidden` (`tests/test_api.cpp`) starts it with `--api`, reads the token from the API file as a client does, uses every endpoint of [Caliper API](../references/api.md), checks that a capture is a PNG of the hidden window's framebuffer that changes when an applet is launched, completes a handshake on the stream, and closes the app with SIGTERM, leaving no process, file or socket. Without a Metal device it is reported as skipped. The window capture's read-back is also checked on its own in `caliper_export_tests`, on that suite's hidden window.

## Embedding and live streaming

`caliper_embed_tests` drives `libcaliper` as a third-party embedder would: it creates an offscreen core, loads the `hello` applet, pumps frames, reads pixels back and shuts down, and it checks the refusal gates. `caliper_live_tests` and `caliper_live_views_tests` cover live streaming, on macOS only, in one process over an offscreen core. See [Live streaming](live-streaming.md). The live page's controls of wire protocol 3.1 are checked at three levels: `caliper_live_tests` checks the page's state on a scripted source (who may control, the rate of `set`, pending values, actions, selections), the native stream against a fake script, and the run bar drawn on an offscreen canvas and clicked through ImGui's input queue (`src/host/live/live_ui_driver.h`). The ctest entry `caliper_app_live_controls` (`tests/test_net_hub.cpp`) starts the real app hidden with `--url` on a hub in the test process, checks the run bar's state while the fake script runs past the step of its last change of state, clicks Pause, types a parameter value, runs an action and shift-drags across a heatmap with `CALIPER_TEST_UI`, and checks what the fake script received and what the page shows of its echo, once with the hub's `--allow-control` and once without.

## The command line

The entries named `caliper_cli_*` (label `cli`) run the `caliper` executable as a user runs it, through `tests/cli_run.cmake`: each checks the exit code and what the run printed. They run with `CALIPER_APPLET_PATH` unset, the user applets folder in the build tree, and `CALIPER_DATA_DIR` on a folder of their own that must still not exist after the run, which proves that the read-only subcommands create nothing in the app-data folder. `caliper_cli_new_builds` (labels `cli` and `sdk`) configures, builds and tests the project that `caliper new` writes against this build's installed SDK.

`caliper_cli_shot_temp` and `caliper_cli_shot_data_dir` (labels `cli` and `shot`) run [`caliper shot`](../references/cli.md#caliper-shot) on the `hello` fixture through `tests/shot_run.cmake`, and `caliper_png_check` checks that the image has the requested size and is not one flat colour. The first runs without `CALIPER_DATA_DIR` and checks that the temporary data folder is gone afterwards and that nothing was created under `HOME`; the second runs with it and checks that the applet's data folder is there and that no `imgui.ini` was written. Without a GPU both are reported as skipped, unless `CALIPER_REQUIRE_GPU=1` makes that a failure.

## Where the tests keep data

No test reads or writes your own app-data folder. ctest runs every entry with `CALIPER_DATA_DIR` on `test-app-data/` in the build folder and with `CALIPER_TEST_RUN=1`, both set in ctest's own environment by the file that `caliper_offline_tests()` writes (`src/builder/cmake/CaliperOfflineTests.cmake`), as the sidecar's offline switch is, so an entry cannot forget them. Entries that keep a folder of their own replace that one: every test binary that opens the stores (`caliper_tests`, `caliper_export_tests`, `caliper_embed_tests`, the live suites and `caliper_catalog_providers_tests`) runs with `CALIPER_DATA_DIR` on `tests/app-data/<binary>`, every command-line test has a `CALIPER_DATA_DIR` of its own, as described above, and every test that starts the hidden app, `caliper shot` or a producer gives that process a folder of its own. Because `CALIPER_DATA_DIR` moves the whole app-data folder, the stores, the applets' data folders, `imgui.ini`, the live session files, the stream files, the API files and the default user applets folder all stay in the build folder. The tests of Caliper LIB (`python/tests/conftest.py`) set `CALIPER_TEST_RUN=1` and give every test a temporary `CALIPER_DATA_DIR`, and the walk-through's dry runs give the app and `train.py` a folder of their own.

The app-data guard backs this up ([Folders and environment variables](../references/environment.md#the-app-data-folder)). A test or hidden run (`--hidden`, `CALIPER_HIDDEN=1`, any `CALIPER_TEST_*` variable, or a test binary, which links `tests/test_run_marker.cpp`) that would resolve to your own app-data folder stops at once with exit code 1 and says so, before it creates anything there. A test binary run by hand, from a shell or an IDE, therefore needs `CALIPER_DATA_DIR`, as ctest gives it. `caliper_test_data_guard` (labels `cli` and `shot`, `tests/data_guard_run.cmake`) runs the suite's typical launches with `HOME` on a stand-in folder: the hidden app with and without a data folder, `caliper_embed_tests` run directly, `caliper shot` in a test run and as you would run it with `--api`, and `caliper.serve()` in a test run. It checks that each refusal happens and that nothing appears in the stand-in's app-data folder. A test that needs another root, such as the embedding tests of `CaliperCoreDesc.data_dir`, sets its own.

## Applet and adapter tests

`caliper_torch_tests` tests the torch adapter in `adapters/torch.hpp`. Five small executables test the learning and simulation code of single applets: `caliper_sculpt_tests`, `caliper_mesh_tests`, `caliper_em_pic_tests`, `caliper_surface_tests` and `caliper_twin_tests`. They link libtorch and are built only when torch is enabled, which keeps the torch link cost out of `caliper_tests`.

## Package and boundary tests

`caliper_sdk_install` (label `sdk`) proves that an applet can build against the installed SDK alone, and that it cannot include `<caliper/embed.h>`. It installs the SDK component of the build into a work folder, copies `tests/sdk_install_probe` and `examples/hello` there, and builds each copy with only `-DCMAKE_PREFIX_PATH` pointing at the install. It then runs the probe, which draws a headless frame with the installed UI stack and calls the fixture host, checks that hello's library and its stamped manifest exist with the expected `[build]` lines, and fails if either build refers to a file in the source tree. `tests/sdk_install_probe/run.cmake` holds the steps, and `CALIPER_SDK_PROBE_DIR` sets the work folder, which CI points outside the checkout. See [SDK package](../references/sdk-package.md).

`caliper_sdk_install` also checks that the SDK holds none of the embedding headers, and builds an applet source that includes `caliper/embed.h` against every SDK target, which must fail because the header is not found. When the build has the embedding library, the test first installs the `caliper-embed` package into the same prefix, so the check holds with both packages installed together: the embedding headers live under an include root of their own.

`caliper_embed_install` (label `embed`) does the same for the embedding package. It installs the embed component alone into a work folder and checks the installed tree, and on macOS it checks that the library exports exactly the C functions that `libcaliper` defines. It then copies `examples/embed_host` there, builds the copy with only `-DCMAKE_PREFIX_PATH` pointing at the install, checks that the build names nothing in the source tree, and runs the copy in its offscreen mode on a copy of the `hello` fixture. Without a GPU the run is reported as skipped, unless `CALIPER_REQUIRE_GPU=1` makes that a failure. `tests/embed_install/run.cmake` holds the steps, and `CALIPER_EMBED_PROBE_DIR` sets the work folder, which CI points outside the checkout. See [Embedding Caliper](../references/embedding.md).

`caliper_host_names_no_applet` (label `boundary`) runs `scripts/check_host_names_no_applet.py`. The script collects the `[applet]` id and name of every manifest under `applets/` and `examples/`, and every window title that their sources pass to `ImGui::Begin()` as a string literal, and fails if any of them is a whole string literal in the code of `src/` or `include/`. Comments are skipped, so a header may cite an applet id as an example. The test is registered only when CMake finds Python 3.

## The builder's suites

With `CALIPER_WITH_BUILDER` on, the default except on Windows, the build also compiles the builder under `src/builder/`, and ctest runs its tests beside the host's. Each module has a doctest executable registered as `builder_<module>`, such as `builder_spec`, `builder_loaders` and `builder_session`. Other entries run `caliper-mcp`, `caliper-acp-harness` and `caliper-builder-host` as child processes against a stub agent, and `builder_agent_py` runs the pytest suite of `caliper-agent`. The cases that run Python need `CALIPER_BUILDER_TEST_PYTHON` to name an interpreter with numpy, pyarrow and the test dependencies of `caliper-agent`; without it they are skipped and say so. `builder_mcp_app` runs `caliper-mcp` against the app when `CALIPER_BUILDER_TEST_APP` names a `caliper` executable, and is skipped otherwise. `ctest --test-dir cmake-build-release -R '^builder_'` runs only these suites. The builder session in the app has its own entries: `caliper_app_session` drives `src/host/builder/app_session.h` with a fake frame loop, and `caliper_app_session_hidden` starts `caliper --hidden --workspace` with a command script ([The workspace](../references/cli.md#the-workspace)) that imports a CSV file, runs its loader, builds and saves a spec applet, captures the frame and renders a panel, then stops the app with SIGTERM and checks the workspace and its journal. `caliper_app_route` is the whole route of an outside agent against the real app: it starts `caliper --hidden --api --api-port 0 --workspace` and, through Caliper API's command endpoints alone, imports a Parquet file and a safetensors file, builds the three-panel dashboard command by command, saves and opens it, renders one panel with `panel.render` and captures the frame, which must not be blank and must differ from the landing screen's; then it runs `caliper-mcp` against the same app, calls one command tool and stops the app with SIGTERM. Its second case runs `caliper shot --launch` on a spec applet that a command script builds in the same run, checks the image of the spec page, and checks that an id the workspace does not have exits with 1. `caliper_app_live_entropy` (`tests/test_app_live.cpp`, macOS) is the acceptance case "plot attention entropy per layer while it trains": `caliper_attention_producer` (`tests/live_attention_producer.cpp`), a test tool with a hub of its own and no torch, streams a model's attention as its heads sharpen, the hidden app attaches with `--url`, and the test builds and opens a spec over the live sources through Caliper API, checks the sources' shapes and rates in the catalog, checks that two captures and two renders of the heatmap taken 3 seconds apart differ, then launches another applet and checks that the stream stays attached and the spec opened again still draws live data. Four more entries of the same file drive the hidden app's landing screen and live page through `CALIPER_TEST_SPEC_UI` beside one or two producers: `caliper_app_live_f4_stream` lists a stream from the stream file that `caliper.serve()` writes (the producer's `--stream-file` writes the same file) and attaches it with F4 and Enter, and checks that its token never shows in the app's output; `caliper_app_live_home_keeps` goes Home from the live page and from the spec page and checks that the stream stays attached, its catalog sources keep arriving and a spec over them keeps drawing live data, then returns with F5 and detaches with ⌘D, after which the sources are gone; `caliper_app_live_second_stream` attaches a second stream from F4, which replaces the first, lets it end while the landing shows, and quits while attached; and `caliper_app_live_drop` drops files on the live page, which open a new spec in build mode beside the live sources, then into the same spec while it has unsaved changes, and into a new one once it is saved. Three more, `caliper_app_save_new`, `caliper_app_save_open` and `caliper_app_save_close`, answer "Save changes to <name>?" through the input driver's `save` step: F3 New dashboard over unsaved changes with Cancel, Don't Save and Save in turn, opening another dashboard from the landing with Save while the open dashboard's own row opens without asking and an `app.launch` never asks, and the driver's `close` with Cancel and then Don't Save, after which the app exits with code 0; a hidden app's SIGTERM over unsaved changes still exits at once. `caliper_app_launch_mcp` launches a dashboard with the API file's token, origin `mcp`, through `POST /v0/applets/{id}/launch` and through `app.launch`: over a saved spec it opens at once, over unsaved changes its `applet.open` waits on an approval card and changes nothing until it is approved (or, denied, at all), and the person's own token opens at once; `caliper_app_launch_agent` does the same from the origin `agent` with a command script's `app.launch`; and `caliper_app_launch_reply` checks the answer of such a launch, `PENDING_APPROVAL` with its note through both ways in, and its card's approval through `GET /v0/approvals/{id}`, while unheld launches answer `ACTIVE`. `builder_mcp_app`'s second case calls `app_launch` through `caliper-mcp` over a spec that the agent never saved and checks that the tool's result and its text say `PENDING_APPROVAL` and that the open waits for the person's approval. Without a Metal device these entries are reported as skipped. The widget agent's inline surface (`src/host/builder/widget_surface.h`) has three: `caliper_widget_surface` drives its state machine headless over a real session with a scripted agent on a hand-moved clock, through every path from Accept to a conflict, and checks its layout as rectangles at two sizes; `caliper_widget_surface_gpu` runs `caliper-widget-shot` over a saved dashboard and checks its PNGs, that the preview changes only the panel's rectangle and that the state after Accept equals a fresh render of the changed spec; and `caliper_widget_surface_agent` drives the real `caliper-agent` through `AcpClient` with the sidecar's scripted model and a fake key, so that nothing leaves its process, and is skipped without `CALIPER_BUILDER_TEST_PYTHON`. `caliper_widget_app` runs `caliper --hidden --api` on a saved dashboard with the sidecar on its scripted model, plays a click, ⌘K, the request and two Enters through `CALIPER_TEST_SPEC_UI`, and checks the four frames it reads back and the journal of the one step committed. Its other cases do the same for a selection's table, a dropped file's question and a property's edit, and the file's case quits the app with its answer still open, which must exit with code 0. Every one of them runs with `CALIPER_AGENT_OFFLINE=1`. The approval cards (`src/host/builder/approval_cards.h`) have two: `caliper_approval_cards` drives them headless over a real session with review on and a hand-moved clock for the queue's time limits (an `mcp` spec edit as a card with its diff, Approve that changes the open spec, Deny that answers `command.denied`, a timeout, a conflict after the spec changed underneath, a destructive command's card, a long command that holds the registry, and the test decisions file) and checks the strip's layout as rectangles at two window sizes with one, three and eight cards and at two text scales; `caliper_approval_cards_app` runs `caliper --hidden --api` with a command script that opens a spec, sends `panel.create` and then `panel.patch` through the real `caliper-mcp`, and approves the first and denies the second through `CALIPER_TEST_APPROVALS` while each call is held, checking that the tool calls answer with the result and with `command.denied` and that the panel is in the open spec. The builder pane (`src/host/builder/builder_pane.h`) has three: `caliper_builder_pane` drives it headless over a real session, gesture by gesture to the three-panel dashboard with one undo step each, with its refusals, drops, the spec text both ways, one history shared with an approved agent edit and a ⌘K Accept, and the spec page's rectangles at two sizes for every combination of build mode, the text strip and the side chat; `caliper_builder_pane_gpu` runs `caliper-builder-shot`, which builds the dashboard through the pane's own input on an offscreen canvas; and `caliper_builder_app` runs `caliper --hidden` on an empty workspace and plays the whole build by hand through `CALIPER_TEST_SPEC_UI`, from the two files dropped on the landing to the saved dashboard opened again from the landing's command line, and checks that the saved spec equals the fixture.

## Tests that need a GPU

A suite that needs a GPU must not report success when it found none. `tests/gpu_skip.h` provides the convention that the gfx, export, embed, live and torch suites share:

- A case with no GPU counts as skipped, prints why, and returns.
- When any case was skipped for want of a GPU and none failed, the executable exits with code 77. `tests/CMakeLists.txt` registers 77 as `SKIP_RETURN_CODE`, so ctest shows the suite as skipped and not as passed.
- A case that can never apply on the platform, such as CUDA on macOS, is counted separately and does not change the exit code.
- With `CALIPER_REQUIRE_GPU=1` a skip for want of a GPU is a failure. A CI lane that must have a GPU sets it, so the lane cannot go green by accident.
- `CALIPER_TEST_FORCE_NO_GPU=1` makes the test environments report no device, so the skip path itself can be tried on a machine that has one.

## Running the tests

```bash
ctest --test-dir cmake-build-release --output-on-failure
```

A ctest label selects a group: `gfx` (`caliper_gfx_tests`), `export` (`caliper_export_tests`), `torch` (`caliper_torch_tests`), `cli` (the command-line tests), `shot` (the `caliper shot` runs), `sdk` and `embed` (the package tests) and `boundary` (`caliper_host_names_no_applet`). For example, `ctest --test-dir cmake-build-release -L gfx` runs only the pixel-exact graphics suite. CI runs the whole set on macOS and Windows; see [Continuous integration](../guides/ci.md).
