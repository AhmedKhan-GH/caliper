# Renderer core, step 9: the TypeScript WebGPU views removed. The references, taken at the step's first commit (2026-11-16)

Taken on the code as it stood before the step: 0313e297 of sprint4-ts9, which is e950ec02 of sprint4-build with
the fourteen review fixes that sprint4-build had then, on the reference Mac (M-series Max, 18 cores, 64 GB,
macOS 27), in Playwright 1.65.0's headless Chromium, with the WebAssembly views built at that head by
scripts/build_wasm.py (Emscripten pinned in web/wasm/emscripten-version.txt) and the colormap's cases written by
caliper_colormap_cases built as .github/workflows/web.yml builds it.

The step changes the browser package only (web/src, its tests and the bundles built from it). No native path
changes, so the benchmarks and counters of "Keeping the fast path as fast" run no changed code and the graphics
suite's rows are untouched. The browser's frame-rate measurements (web/test/perf.spec.ts and wasm.spec.ts's
"orbit at an interactive rate") were not run: timing was held back while the GPU was in use.
The webgpu project, which draws on the machine's GPU, was not run for the same reason; the TypeScript WebGPU
views' pictures below are SwiftShader's.

## Where the TypeScript WebGPU views drew

Before the step the element's own views drew heatmaps, images and points with WebGPU (web/src/render/gpu.ts,
heatmap-gpu.ts, points-gpu.ts) whenever the page had an adapter, that is in the webgpu and swiftshader projects,
and with Canvas 2D in the canvas2d project. Series and histograms were always Canvas 2D. These are every test
page on which they drew with WebGPU, with the capture each saved (CALIPER_SHOTS, <name>-swiftshader.png):

| Spec | Tests | What the TypeScript WebGPU views drew | Captures |
|---|---|---|---|
| views.spec.ts | heatmap (5), image, points (4), the picker, the status dot | Heatmaps of 4 x 8 and 8 x 8 cells, a 2 x 3 RGBA image, 2-D points of four classes and a 3-D spiral of 2,000 points in magma; each asserted renderer "webgpu" and the colour of every cell, pixel or point | heatmap, image, picker, points-2d, points-3d |
| fallback.spec.ts | auto without the WebAssembly views | The viewer page's two heatmaps, image and points; asserted renderer "webgpu" | none |

The notebook checks python/tests/test_widget.py and test_live_training_notebook.py also expected "webgpu" in
their metal mode when the package has no WebAssembly views; they were not run.

The TypeScript WebGPU views' pictures and those of the same tests on Canvas 2D (scratch tool pngdiff.mjs on

## After the step, the same commands on the step's code

web/src/render/gpu.ts, heatmap-gpu.ts and points-gpu.ts are deleted, with the WebGPU branches of
views/heatmap.ts and views/points.ts (and the points view's canvas under its WebGPU canvas), the device in the
views' host, the element's request for a device, its list of kinds that needed one, its handling of a lost
device and its wait on the GPU in settled(), the threshold search of render/colormap.ts (colormapThresholds,
thresholdIndex), which only the WebGPU heatmap and its test used, and the plate colour for GPU clears
(PLATE_RGBA). The element keeps hasAdapter() in wasm.ts, which chooses the WebAssembly views. Its debugState's
adapter now comes from the WebAssembly views' counters.

## The Canvas 2D captures against those from before

In the canvas2d project every capture of the element's own views is byte for byte the same as before: heatmap,
image, picker, points-2d, points-3d, series, series-log, histogram, page, points3d-box-ts, points3d-cues-ts, the
eight edges-*-ts captures and the three linked-* captures, 22 of 22 with 0 differing bytes of RGBA.

In the swiftshader project the element's own views now draw with Canvas 2D: views.spec.ts, fallback.spec.ts and
e2e.spec.ts assert renderer "canvas2d" there, and edges.spec.ts and views.spec.ts check the colour of every cell,
pixel and point. Its Canvas 2D pictures are not those of the canvas2d project (738 of 201,600 pixels differ for the
heatmap, at most 25 levels, at the text and the cell edges), because the browser rasterises Canvas 2D on
SwiftShader under that project's flags. Its series, series-log and histogram captures, which were Canvas 2D before
too, are byte for byte the same as before.

## Where each case is covered now

| Case drawn by the TypeScript WebGPU views before | Covered after the step by |
|---|---|
| views.spec.ts: heatmap, image, points, picker, status dot | The same tests drawing with Canvas 2D in all three projects, asserting renderer "canvas2d" and every colour; the WebAssembly views' heatmaps, images and points with the same data and gestures in wasm.spec.ts (the fixed views, selections, pan and zoom, and the module's comparison of each heatmap texture with map_f32_to_rgba8) |
| fallback.spec.ts and e2e.spec.ts, the viewer page without the WebAssembly views | The same tests, now asserting "canvas2d" for every view; the same page with the WebAssembly views is wasm.spec.ts's first test |
| edges.spec.ts, every colormap edge case | renderer="ts" with Canvas 2D and renderer="wasm" with WebGPU side by side in the webgpu and swiftshader projects, Canvas 2D alone in canvas2d |
| points3d.spec.ts, box, camera, cues, rotate | The WebAssembly views compared with the Canvas 2D view in the webgpu and swiftshader projects, as the design asks |
| linked.spec.ts and controls.spec.ts, the second page | The same tests, the second page drawing with Canvas 2D |
| perf.spec.ts, 100,000 points on the GPU | wasm.spec.ts's "100,000 points orbit at an interactive rate on the GPU" for the WebGPU path; perf.spec.ts now measures the Canvas 2D view at 100,000 and 20,000 points in canvas2d only, where the element's own views draw as they do everywhere |
| colormap.spec.ts, the WebGPU threshold search against the native table | Nothing: the search is deleted with the only renderer that used it. The browser's exact GPU colours are the WebAssembly views', checked by the module against map_f32_to_rgba8, by shaders.spec.ts's colormap by keys against the C++ cases, and by wasm.spec.ts's colormap keys against the native case file. colormapInto and lutIndex keep their checks against the table and the C++ cases |

Coverage lost with the deleted path: the TypeScript views drawing with WebGPU itself, their recreation with
Canvas 2D after a lost device (which no test exercised), and the threshold search. Every case that a remaining
path draws is still tested.
